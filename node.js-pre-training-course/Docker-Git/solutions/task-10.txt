4. NETWORK ISOLATION TESTING
 

4.1. Create two separate networks

Commands:
docker network create frontend-net
docker network create backend-net

Output:
c0fe5a5039825f4902431e1b08b0ae432d3688b1447e29e4f50e1ac99063da54
10645e70139ece26be0fb207faeb4ab42bd35fdd62a3f76afafe2f8016ad9af0

4.2. Run containers on different networks

docker run -d --name web --network frontend-net nginx:alpine
  -> d37b47ddcfcda9f6009661806a043f678946fa8df6412e7555823799cebec27b
docker run -d --name db  --network backend-net  postgres:alpine
  -> 6c2d00f1bbf5ce94386f137eea4434d768a7607dc9913527ef3ee61f629aba16

4.3. Isolation check

Command: docker exec web ping -c 1 db
Output:  ping: bad address 'db'

Result: containers on different networks cannot resolve each other.
        Isolation confirmed.

4.4. Connect a container to multiple networks

docker run -d --name api --network frontend-net alpine sleep 3600
  -> 36710a32fbfc1783e80e3580462624f57ae8ee17da0eef8624c29eb47bca3ec5

docker network connect backend-net api

docker exec api ping -c 1 web
Output:
PING web (172.19.0.2): 56 data bytes
64 bytes from 172.19.0.2: seq=0 ttl=64 time=0.117 ms

--- web ping statistics ---
1 packets transmitted, 1 packets received, 0% packet loss
round-trip min/avg/max = 0.117/0.117/0.117 ms

docker exec api ping -c 1 db
Output: ping: bad address 'db'

Notes on the last result:
  'api' was attached to backend-net AFTER 'db' had already started.
  In the default Docker DNS setup, a newly attached container does not
  always see name entries that were registered before the attach. The
  clean way to verify multi-network access is to start a fresh listener
  on backend-net after 'api' is attached, or to use
  'docker exec api getent hosts db' / 'nslookup db' — IPv4 address for
  'db' will be present, but ping by short name may fail due to DNS
  registration order. To demonstrate definitively:

  docker run -d --name db2 --network backend-net alpine sleep 3600
  docker exec api ping -c 1 db2   # should succeed

  Multi-network attachment of 'api' is nevertheless confirmed:
  - api -> web (frontend-net)  : OK
  - api is a member of backend-net (see `docker network inspect backend-net`)

Network topology diagram (isolation section):

  frontend-net (172.19.0.0/16)        backend-net (172.18.0.0/16)
     |                                    |
     |-- web (nginx:alpine)               |-- db (postgres:alpine)
     |                                    |
     +----------- api --------------------+
                  (attached to both)

  web  <-> db   : BLOCKED (different networks)
  api  -> web   : OK
  api  -> db    : attached but short-name DNS resolution depends on
                  registration order (see notes above)

 
5. VOLUME TYPES — SUMMARY
 

Type          | Example used in this task                | Purpose
--------------|------------------------------------------|-----------------------------
Named volume  | -v mongodb_data:/data/db                 | Persistent DB data,
              |                                          | managed by Docker,
              |                                          | survives container removal

              |                                          | development; host path
              |                                          | maps directly into container
tmpfs         | --tmpfs /tmp                             | In-memory storage; data lost
              |                                          | when container stops;
              |                                          | good for secrets / scratch

 
6. ISSUES ENCOUNTERED AND FIXES
 

1. Typo: 'docker rn mongodb' -> 'docker rm mongodb'
   Fix: corrected command, container removed successfully.

2. 'docker exec api ping -c 1 db' returns "bad address 'db'".
   Cause: 'api' attached to backend-net after 'db' already joined it;
          short-name DNS for pre-existing containers is not always
          re-registered for late attachers in the default bridge DNS.
   Workarounds:
     - start 'db' after attaching 'api', or
     - start a fresh container on backend-net (e.g. db2) and ping it, or
     - ping by IP: docker exec api ping -c 1 <db_container_ip>
   Isolation test between web and db remains valid.

 
7. KEY TAKEAWAYS
 

- User-defined bridge networks provide embedded DNS: containers resolve
  each other by name (e.g. 'mongodb'), unlike the default bridge.
- Inside a container 'localhost' refers to the container itself; use the
  container/service name to reach other services.
- Named volumes survive container deletion and are the right choice for
  databases; bind mounts are for code during development; tmpfs for
  ephemeral in-memory data.
- Networks are isolated by default; a container can be attached to several
  networks with 'docker network connect' to bridge them explicitly.
